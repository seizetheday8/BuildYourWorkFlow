## 1. 四个端

| 端 | 代号 | 位置 | 核心能力 |
|----|------|------|---------|
| DeepSeek 网页端 | **DS** | 云端 | 架构设计、技术决策、文档主笔 |

## 2. 四条硬规则

### 规则 1 · 主笔唯一
一份文档同一时间只由一端主笔。其他端只能审阅，不能直接改写。
主笔变更需要 DS 明确宣布。

### 规则 2 · 落盘唯一 + verbatim 原则
**只有 CC 能对本仓库执行写操作**（创建、修改、git commit、git push）。

**verbatim 原则**：CC 在执行落盘时，必须逐字复制收到的内容。
CC 若认为内容有问题（错别字、格式错误、逻辑冲突），**只能汇报，不能自行修改**。
汇报后等待 DS 下一轮指令。

主笔权归属 DS（或其他被指定端），写入权归属 CC。两者冲突时：
**CC 停下汇报，由 DS 裁决。**

### 规则 3 · 信息回流
任何一端的输出，必须回流到 DS，由 DS 决定是否采纳、如何修订。
禁止"CC 直接采纳 GPT 意见"或"CC 自己发挥"。

### 规则 4 · 审阅请求必须携带 commit hash
任何提交给 GPT / CX 审阅的内容，必须附带：

- 仓库 URL
- **精确的 commit hash**（短 hash 至少 7 位）
- 相关文件路径

禁止用"最新版"、"刚才那个"等模糊指代替代。
理由：云端对话无版本号，靠 commit hash 唯一锚定被审对象。

## 3. 信息流向

### 3.1 标准闭环（默认）

    ① DS 提出变更（给出完整内容 + 目标文件路径）
         ↓ 用户复制
    ② CC 落盘 + commit + push，汇报 commit hash
         ↓ 用户复制仓库 URL + commit hash
    ③ GPT 红队审阅
         ↓ 用户复制审阅意见
    ④ DS 决定采纳 / 否决 / 修改
         ↓ 用户复制下一轮变更
    ⑤ CC 落盘 + commit + push
         ↓ 闭环完成

每轮只推进一个主题。主题完成后才开下一轮。

### 3.2 快速通道（例外）

以下**低风险、无歧义**的变更，CC 可直接执行并汇报，不经过 DS 前置批准：

- 修复 commit message 拼写错误（尚未 push 时）
- 修正文档中的错别字、格式、标点
- 文件重命名（同一目录内）
- 补充 `.gitignore` 中遗漏的忽略项

**快速通道限制**：
- CC 执行后必须在汇报中明确标注 `[快速通道]`
- 每次快速通道操作独立成一个 commit
- DS 有权要求回滚任何快速通道变更
- 涉及内容含义变化的修改，**不属于快速通道**

## 4. 异常路径

### 4.1 测试失败返工
CC 运行测试失败时：
1. 立即停止
2. 汇报：失败用例、报错原文、已尝试的排查
3. 等待 DS 判断是"实现问题"还是"测试设计问题"
4. DS 给出返工指令后才继续

**例外**：无争议的环境问题（如依赖未安装）可直接处理，但需在汇报中标注。

### 4.2 并行任务
不同文件的独立变更，允许多轮并行。但**同一文件的变更严格串行**。
并行任务需在指令中显式标注 `[并行]`。

### 4.3 DS 暂时不可用
若 DS 无法响应，项目**暂停**。
CC 不得接受来自 GPT / CX / 用户的架构级变更指令，只能执行快速通道。
需要紧急决策时，暂停比错更快。

### 4.4 两端结论冲突
GPT 意见与 DS 决策冲突时，**以 DS 为准**。
DS 在裁决时需说明采纳或不采纳 GPT 意见的理由，记录在下一版文档中。

### 4.5 错误提交回滚
发现已 push 的 commit 有严重错误：
1. CC 汇报问题 commit 的 hash
2. DS 决定：`git revert`（保留历史）或 `git reset + force push`（重写历史）
3. **默认用 revert**。force push 仅在 commit 尚未被任何端引用时允许
4. 回滚后必须新建 commit，不得 amend

### 4.6 仓库状态不明
任何一端发现仓库状态可疑（未提交文件、意外分支、远程不一致）：
1. 立即暂停所有写操作
2. CC 执行只读自查（`git status` / `git log` / `git remote -v`）
3. 汇报原始输出
4. 等 DS 确认后再继续

## 5. 职责边界细化

### 5.1 测试归口
- **测试设计**（测什么、断言什么）：DS 负责
- **测试实现**（写测试代码）：CC 负责
- **测试运行**：CC 负责
- **测试结果解读**：DS 判断是否通过、是否需要返工

### 5.2 CX 接入前的准备
CX 当前未接入。接入前必须：
1. 在本文档中明确其职责边界
2. 定义其输出如何回流（默认：CX 输出作为参考，不直接落盘）
3. DS 明确宣布接入时机

### 5.3 CC 的执行纪律
CC 收到的每条指令应包含：
1. 任务目标
2. 明确的禁止事项
3. 验收标准
4. 汇报格式

CC 在任何步骤失败时**立即停止并汇报**。
禁止 CC 在未获指令时主动修改仓库。

**docs 编号规则**：
- `00` 保留为总览
- `01-09` 为项目核心文档
- `10+` 为专项记录
- 编号一旦分配不再重排

## 7. Commit Message 约定

格式：`<类型>(<范围>): <描述>`

| 类型 | 用途 |
|------|------|
| `docs` | 文档变更 |
| `feat` | 新功能 |
| `fix` | 修 bug |
| `refactor` | 重构 |
| `chore` | 杂项 |
| `test` | 测试 |

范围可选，涉及代码模块时建议带上。
