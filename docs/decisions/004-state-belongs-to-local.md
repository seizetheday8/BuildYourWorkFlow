# 004 · 状态归仓库，推理归模型

## 决策

跨时间的一致性由**仓库**维护，不由**模型**维护。

## 备选项

**A · 让模型记住一切**
- 缺点：网页端无长期记忆；即使有也不可控、不可审计

**B · 状态归仓库，推理归模型（选中）**
- 优点：一致性可控、可审计、可版本控制
- 缺点：每次任务前需先读仓库

## 理由

1. 网页端模型"不可控"：新会话忘记上次推理过程，
   可能对同一条规则今天赞同、明天反对
2. 模型强在**推理**，弱在**一致性**——两件事分开
3. 一致性从仓库来：每次决策写进 `docs/decisions/`
4. 下次模型做新决策前，先读 `docs/decisions/`

## 角色重定义

网页端**不是"架构大脑"，是"被召唤的顾问"**：
- 不召唤它，它不存在
- 召唤它时，先读仓库（当前状态 + 历史决策）
- 基于这些做推理，输出建议
- 建议被采纳/否决后写进仓库
- 然后它"忘掉"，下次重新读

## 真正的决策者

**用户 + 仓库。**

- 用户：最终裁决、承担后果
- 仓库：记录状态和决策历史
- DS：推理引擎（每次临时调用）
- CC：执行 + 落盘
- GPT：独立审阅
- CX：验证

"决策者"不是一个 AI，是一个系统。
